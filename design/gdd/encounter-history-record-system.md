# 奇遇历史记录系统

> **状态**: 设计中
> **作者**: 用户 + 代理
> **最后更新**: 2026-04-25
> **实现支柱**: 支柱3：奇遇驱动的成长

## 概述

奇遇历史记录系统采用"轻量级日志 + 图鉴式展示"的设计，通过记录奇遇的核心元数据（基础标识、时空上下文、结果奖励、玩家状态快照）为玩家提供成就感和回顾乐趣。系统利用2D俯视角的优势，实现事件驱动即时写入机制，既保证了数据完整性，又避免了复杂的数据库查询系统。

玩家通过图鉴式UI界面查看奇遇历史记录，按时间倒序浏览已触发的奇遇，查看详细信息，并获得统计反馈（总触发次数、已发现奇遇总数/总奇遇数）。系统支持类型筛选、排序和搜索功能，稀有奇遇使用特殊着色和图标，新纪录显示"NEW"标签。

如果没有这个系统，游戏将失去成就感与调试能力，玩家无法回忆重要奇遇的触发细节，缺乏收集所有奇遇的动力，开发者调试困难，叙事体验变得碎片化。该系统是实现"奇遇驱动的成长"游戏支柱的重要支撑，利用Steam平台的PC硬件优势提供高效的内存管理、快速UI渲染和可靠的持久化存储。

## 玩家幻想

玩家应该能够体验到"江湖历历在目"、"事事有迹可循"的武侠核心幻想，通过奇遇历史记录系统回顾自己的江湖历程，直接体验到作为主角的成长轨迹和奇遇收集的成就感。

直接层面：玩家在游戏过程中或结束后积极查看奇遇历史记录，在图鉴式UI中浏览已触发的奇遇，查看详细信息，获得统计反馈。这是显性的回顾和收集过程，直接决定了玩家的成就感和探索动力。玩家应该能够清晰地看到每个奇遇的触发时间、地点、结果和奖励摘要，从而回忆起具体的江湖经历。

间接层面：奇遇历史记录的底层逻辑（如事件驱动写入、内存管理、持久化存储）由系统自动处理。玩家在后台不可见这些计算过程，只体验到最终的结果（完整的奇遇历史记录、准确的统计信息）。这种无缝的体验让玩家专注于江湖回忆和收集乐趣，而不是技术细节。

参考游戏实现：
- 《巫师3》的冒险日志系统，通过详细的任务和事件记录提供沉浸式叙事体验
- 《原神》的图鉴系统，通过收集进度和详细信息提供成就感和探索动力
- 《暗黑破坏神4》的事件历史记录，通过简洁的列表和统计信息帮助玩家追踪游戏进度

## 详细设计

### 核心规则

1. **记录内容**（核心元数据）：
   - **基础标识**（Basic Identification）：
     - Encounter ID：奇遇的唯一标识符
     - Title：奇遇名称（如："破庙避雨"、"强盗伏击"）
     - Type：奇遇类型（战斗、叙事、资源、环境）
   - **时空上下文**（Spatio-Temporal Context）：
     - Timestamp：游戏内日期和时间（如：第3年-春-子时）
     - Location：触发时的地图区域名称（如："青云山-后山"）
     - Weather：当时的天气状态（可选，用于复盘特定天气奇遇）
   - **结果与奖励**（Outcome & Rewards）：
     - Outcome：玩家的选择或结果（如："帮助老者"、"击败强盗"、"无视"）
     - Rewards Summary：简略的奖励列表（如："银两x50, 经验x200"），不记录具体物品ID以节省空间
   - **玩家状态快照**（Player State Snapshot）：
     - Player Level/Realm：触发时的角色等级或境界
     - Key Stats：当时的福缘值或善恶值（用于分析运气对奇遇的影响）

2. **记录机制**（事件驱动即时写入）：
   - **触发时机**：
     - 当EncounterManager判定奇遇结束（对话结束或战斗胜利）时，立即调用HistoryLogger.log_encounter()
   - **数据结构**：
     - 使用简单的列表Array[Dictionary]在内存中维护最近N条记录（如：最近100条）
     - 同时维护Dictionary用于统计：{"encounter_id": count}，快速查询某奇遇触发次数
   - **持久化策略**：
     - 全量保存：在游戏退出或手动保存时，将整个历史列表序列化并写入存档文件
     - 直接存入主JSON存档，避免复杂的文件分离策略

3. **查询和展示**（图鉴式UI）：
   - **界面布局**：
     - 左侧列表：按时间倒序排列的奇遇标题列表，选中项高亮
     - 右侧详情：显示选中奇遇的详细信息（时间、地点、结果、奖励摘要）
     - 顶部统计栏：显示总触发次数、已发现奇遇总数/总奇遇数（如：45/120）
   - **筛选与排序**：
     - 类型筛选：按钮切换显示"全部"、"战斗"、"叙事"、"资源"
     - 排序：默认按"最新触发"，可切换为"最早触发"
     - 搜索：简单的字符串匹配搜索标题
   - **视觉反馈**：
     - 新纪录标记：新触发的奇遇在列表中显示"NEW"标签，查看后消失
     - 稀有度着色：稀有或隐藏奇遇的标题使用金色或紫色字体
     - 图标化：每个奇遇类型对应一个小图标（剑、书卷、宝箱、云朵）

4. **Steam平台优化实现**：
   - **高效内存管理**：使用对象池技术重用历史记录对象，减少GC压力
   - **快速UI渲染**：预加载图鉴UI模板到内存，触发时只需更新内容
   - **可靠持久化存储**：利用PC硬盘性能快速读写JSON存档文件
   - **音频沉浸感**：打开历史记录界面时播放轻柔的传统乐器音效，增强回顾氛围

### 状态和转换

- **未记录状态**：奇遇尚未触发或正在触发中
- **记录生成状态**：奇遇结束后，系统生成历史记录对象
- **内存存储状态**：历史记录存储在内存列表中，等待持久化
- **持久化状态**：历史记录已写入存档文件，可在下次游戏加载
- **UI展示状态**：玩家打开历史记录界面，系统渲染图鉴式UI

状态转换流程：
- 未记录 → 记录生成：奇遇结束，EncounterManager发出完成信号
- 记录生成 → 内存存储：HistoryLogger创建记录对象并添加到内存列表
- 内存存储 → 持久化：游戏保存时，SaveManager将历史列表写入存档
- 持久化 → UI展示：玩家打开历史记录界面，系统从存档加载并渲染UI
- UI展示 → 内存存储：玩家关闭界面，系统保持内存中的活跃记录

### 与其他系统的交互

- **奇遇系统**（EncounterSystem）：
  - 数据输入：接收encounter_finished(id, outcome, rewards)信号
  - 功能输出：提供历史记录查询接口，支持奇遇系统的调试需求
- **世界状态持久化系统**（WorldStatePersistence）：
  - 数据输入：在存档数据结构中添加encounter_history: Array和encounter_stats: Dictionary
  - 功能输出：提供加载逻辑，从存档恢复历史列表用于填充UI
- **奇遇数据库**（EncounterDB）：
  - 数据输入：通过ID从EncounterDB读取完整的描述、背景故事和完整奖励表
  - 功能输出：支持is_hidden_in_log: bool字段，某些隐秘奇遇可选择不记录
- **UI系统**：
  - 数据输入：接收历史记录列表和统计信息
  - 功能输出：渲染图鉴式UI、处理筛选/排序/搜索交互、显示新纪录标记

## 公式

### 历史记录存储大小公式

`存储大小 = 记录数量 × 平均记录大小`

**变量:**
| 变量 | 符号 | 类型 | 范围 | 描述 |
|------|------|------|------|------|
| 记录数量 | record_count | int | 0-1000 | 历史记录的总数量 |
| 平均记录大小 | avg_record_size | int | 100-500 | 每条记录的平均字节数 |
| 存储大小 | storage_size | int | 0-500000 | 总的存储大小（字节） |

**输出范围:** 0到500000字节（0KB到500KB）
**示例:** 当记录数量为100，平均记录大小为200时，存储大小 = 100 × 200 = 20000字节（20KB）

### 统计查询时间复杂度公式

`查询时间 = O(1) + O(log N)`

**变量:**
| 变量 | 符号 | 类型 | 范围 | 描述 |
|------|------|------|------|------|
| 统计字典查找 | O(1) | constant | - | 通过encounter_id直接查找统计信息 |
| 记录列表排序 | O(log N) | logarithmic | - | 对N条记录进行排序的时间复杂度 |
| 查询时间 | query_time | time | - | 总的查询时间复杂度 |

**输出范围:** O(1)到O(log N)
**示例:** 当需要查询某奇遇的触发次数时，时间复杂度为O(1)；当需要按时间排序所有记录时，时间复杂度为O(log N)

### 内存占用估算公式

`内存占用 = 活跃记录数 × 记录对象大小 + 统计字典大小`

**变量:**
| 变量 | 符号 | 类型 | 范围 | 描述 |
|------|------|------|------|------|
| 活跃记录数 | active_records | int | 0-100 | 内存中维护的活跃记录数量 |
| 记录对象大小 | record_object_size | int | 200-1000 | 每个记录对象的内存占用（字节） |
| 统计字典大小 | stats_dict_size | int | 1000-10000 | 统计字典的内存占用（字节） |
| 内存占用 | memory_usage | int | 1000-110000 | 总的内存占用（字节） |

**输出范围:** 1000到110000字节（1KB到110KB）
**示例:** 当活跃记录数为100，记录对象大小为500，统计字典大小为5000时，内存占用 = 100 × 500 + 5000 = 55000字节（55KB）

## 边缘情况

- **如果Steam平台存储空间不足**：系统将显示错误提示"历史记录存储空间不足"，建议玩家清理存档或减少记录数量。
- **如果网络连接中断**（单机模式不影响）：在未来的多人模式中，系统将保存本地历史记录，等待网络恢复后同步数据。
- **如果历史记录文件损坏**：系统将检测JSON格式有效性，如果损坏则创建新的空历史记录文件，并记录警告日志。
- **如果内存不足无法加载所有历史记录**：系统将优先加载最近的100条记录，其他记录按需从存档文件加载。
- **如果奇遇ID在数据库中不存在**：系统将跳过该记录的详细信息显示，在UI中标记为"未知奇遇"，并记录错误日志。
- **如果存档文件过大**（>1MB）：系统将实施数据压缩优化，如果仍超过限制则显示"历史记录过大，已启用精简模式"并移除非关键字段。

  - **Godot 4.6引擎**：利用Godot的信号系统、JSON序列化和UI系统

- **统计字典大小**：5000字节（可调整范围：1000-10000字节）

## 验收标准

- **GIVEN** 玩家完成一个奇遇事件，**WHEN** 奇遇历史记录系统接收encounter_finished信号，**THEN** 系统正确生成历史记录对象并添加到内存列表中。
- **GIVEN** Steam平台存储空间有限（<100MB），**WHEN** 游戏保存时写入历史记录数据，**THEN** 系统成功将历史记录序列化并写入存档文件，总大小不超过1MB。
- **GIVEN** 游戏运行在不同分辨率的设备上（1920x1080到3440x1440），**WHEN** 玩家查看奇遇历史记录界面，**THEN** UI元素正确适配屏幕尺寸，保持清晰可读。
- **GIVEN** 玩家触发一个新的稀有奇遇，**WHEN** 查看历史记录界面，**THEN** 系统在列表中显示红色"NEW"标签，奇遇标题使用金色字体，并播放特殊的钟磬音效。
- **GIVEN** 历史记录文件损坏，**WHEN** 玩家尝试加载游戏，**THEN** 系统检测JSON格式有效性，创建新的空历史记录文件，并记录警告日志。
- **GIVEN** 玩家在历史记录界面搜索特定关键词，**WHEN** 输入搜索词，**THEN** 系统实时过滤列表，高亮匹配的关键词，支持简单的字符串匹配。
- **GIVEN** 内存不足无法加载所有历史记录，**WHEN** 玩家打开历史记录界面，**THEN** 系统优先加载最近的100条记录，其他记录按需从存档文件加载。
- **GIVEN** 奇遇ID在数据库中不存在，**WHEN** 系统尝试显示详细信息，**THEN** 在UI中标记为"未知奇遇"，跳过详细信息显示，并记录错误日志。
